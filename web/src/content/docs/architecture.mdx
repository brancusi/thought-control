## The whole system

<Fig n="1" wide caption="Everything on one sheet. Writes run left to right along the top of the core and land in this device's log; reads run right to left along the bottom, out of a store that is only a cache of the log.">
  <SystemMap />
</Fig>

Read it from the edges in. **Surfaces** at the top are every way in: you at the CLI or in the
TUI, an agent running the same CLI (or steering the TUI through its socket), a file dropped into
`drop/`, a round trip through `$EDITOR`, the menu bar. None of them has behaviour of its own; they
all call **thc-core**.

A **write** is parsed once (`due:fri` becomes a date field and is never re-read from text), turned
into validated operations by the builder, checked against the actor's policy and any
preconditions, then committed: lock, catch up, stamp each event with a hybrid logical clock,
append to `log/<this-device>/`, fsync, apply to SQLite. A **read** compiles a query into one SQL
`WHERE` over the store and renders rows, as JSON or for people.

At the bottom, the **vault** is a plain folder you sync with whatever you like. Only the log in
it is the truth. The **store** next to it is a cache in the local cache directory: delete it and
`thc rebuild` replays the log into an identical one.

## The rules of the house

Every page in this section follows from a short list. When something in the code looks odd,
it usually traces back to one of these.

<ol class="laws">
  <li><p><strong>The log is the truth.</strong> Every change is one JSON line, appended, never rewritten. The SQLite store, the Markdown export and every screen are derived from it.</p></li>
  <li><p><strong>Replay is a pure function of the events.</strong> Clocks, randomness, timezones and recurrence math live in the writer. Two devices with the same lines build the same state, byte for byte.</p></li>
  <li><p><strong>One writer per file.</strong> A device appends only to its own log directory, so a sync tool never sees two writers on one file and never makes a "conflicted copy".</p></li>
  <li><p><strong>One primitive.</strong> A page, a day, a task, a tag and a saved view are all nodes. "Task" is a status, "reminder" is an alert. Fewer kinds, fewer edge cases.</p></li>
  <li><p><strong>Text at the edges, structure in the core.</strong> Capture syntax is parsed once, into typed fields. Stored text is never re-parsed to learn what something is.</p></li>
  <li><p><strong>The CLI is the API.</strong> People and agents use the same commands, with <code>--json</code>, stable exit codes and attribution on every write.</p></li>
  <li><p><strong>State is serializable, or it is a bug.</strong> The TUI is one <code>UiState</code>, changed only by messages, drawn by a pure view. What isn't in the state can't be replayed, patched or tested.</p></li>
  <li><p><strong>One source of truth, instantiated.</strong> A document lives in one place and every view holds a reference to it. The same component appears wherever that thing does; differences are data, not a second code path.</p></li>
</ol>

## The life of a write

Follow one command all the way down:

```sh
$ THC_ACTOR=claude thc todo "Call the dentist due:fri #health !high"
```

1. **Parse.** `capture.rs` splits the text into words, finds `due:fri`, `#health` and `!high`,
   resolves `fri` against the writer's clock and timezone, and keeps the rest as text.
2. **Build.** `TxBuilder` makes the operations: today's journal day if it doesn't exist yet
   (its id is keyed from the date, so every device makes the same one), a `node.create` for the
   task with a fresh 12-character id, a fractional order key after the last sibling, and its
   status, due and priority as props, the `health` tag (keyed from its name), and an `edge.add`
   linking the two.
3. **Check.** The actor `claude` is an agent, so its tier in the device config decides whether
   this verb is allowed, needs confirmation, or is refused. `--expect` and `--if-match` would be
   checked here too, under the lock.
4. **Commit.** `Vault::transact` takes the device write lock, catches up on any lines it hasn't
   applied, stamps each op with the HLC, the device id, the actor and one shared transaction id,
   appends the lines, fsyncs, and applies them to SQLite in one transaction.
5. **Notify.** The daemon, if it runs, sees the append and pushes `changed` to every subscriber.
   An open TUI flashes the new row, marked `◆ claude`. The transaction sits in `thc review` until a
   person accepts or reverts it.

## The life of a read

```sh
$ thc q 'status:open due<=+3d #health sort:due' --json
```

The query compiler parses the terms into an AST (which `--explain` prints in plain words) and
one SQL `WHERE` over `nodes`, with relative dates resolved once. SQLite answers from partial
indexes on open tasks. The output layer renders node objects with a stable, additive JSON shape.
No daemon is involved: the CLI opens the store directly, because a round trip through a socket
would cost more than it saves.
